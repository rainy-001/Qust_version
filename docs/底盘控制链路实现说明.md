# 底盘控制链路实现说明（omni 四全向轮步兵）

> 本文记录本轮变更：把原来的"外设骨架"接成一条真正能跑的底盘控制链路
> —— **遥控器 → 底盘 C 板 → 四路 M3508**，并按"硬件未就绪"的要求预留了超级电容与功率控制接口。
> 全部实现依赖 `sp_middleware/`（同济 SP 开源电控中间件），没有引入第三方代码。

## 1. 变更概览

改造前：`applications/can_task.cpp` 只是 GM6020 的 bring-up 测试，每 1 ms 对一台 6020 发 0 V，
四个轮子没有任何代码去驱动。

改造后：一个 `chassis_task` 独占 CAN1，1 ms 周期跑完整条链路，四路 M3508 闭环驱动。

```text
DBus 遥控器 ──USART3──► uart_task.cpp（既有，中断收帧 + 解析）
                              │ remote.ch_rv / ch_rh / ch_lh
                              ▼
              chassis_task.cpp   chassis_step()      ← 1ms 固定节拍
                    │  ① 仲裁：遥控器 + 4 台电机全部在线才动作
                    │  ② 摇杆 → (vx, vy, wz)，含死区与限幅
                    │  ③ sp::Omni::calc()   → 四轮目标转速 rad/s
                    │  ④ 4 × sp::PID        → 四轮力矩 N·m
                    │  ⑤ 功率/电流上限（预留接口）
                    │  ⑥ 4 × write() + 1 × send(0x200)
                              ▼
              CAN1 1Mbps 标准帧 0x200 ──► M3508 ×4（LF / RF / LR / RR）
                    ▲
                    └── HAL_CAN_RxFifo0MsgPendingCallback → 0x201~0x204 → motor.speed（速度环反馈）
```

## 3. 关键实现决策

1. **一个任务独占 CAN1**
   发送在任务上下文、接收在自己的 FIFO0 回调里，全局只有一份 `sp::CAN` 对象，
   不存在多个任务抢发送邮箱的问题；将来超电/云台的帧也在同一处收发。

2. **四台电机共用一帧 0x200**
   `RM_Motor::write()` 只写自己那 2 字节（下标 `(id-1)%4*2`），四台都写完后 `send()` 一次。
   发送前先判 `HAL_CAN_GetTxMailboxesFreeLevel()`，避免 HAL 静默丢帧
   （丢一帧的表现是"该电机保持上一拍电流"）。

3. **失联即归零（不用"半残"控制）**
   遥控器或**任意**一台电机超过 100 ms 没有数据，立即四路 `cmd(0)` + `PID::clear()` + 下发。
   清积分是必要的：否则积分残留会让恢复连接的瞬间猛冲一下。

4. **速度环使用带积分分离的重载**
   `PID::calc(set, fdb, kIntegralPause)`：|比例项| 较大时本拍不积分，误差收敛后才开始积分。
   这是仿真里"全程超调 < 0.1%"的直接原因。

5. **量纲一次性对齐，不做二次换算**
   `RM_Motor` 构造时传减速比 `3591/187`，于是 `motor.speed` 就是**轮端 rad/s**
   （正好是 `omni.calc()` 的输出单位），`motor.cmd()` 的入参就是**输出轴 N·m**。
   厂商手册（《M3508 使用说明 V1.0》特征参数）给出的是**输出轴口径**：
   转矩常数 **0.3 N·m/A**、额定（最大连续）**3 N·m @ 10 A**、堵转 **4.5 N·m**，
   即 1 N·m ≈ 3.3 A；C620 输出 20 A 时约 6 N·m，但那是短时峰值。
   本工程的 `kMaxTorque = 1.2 N·m` 只有额定连续的 40%，热上是安全的。

## 4. 参数表

`applications/chassis_task.cpp` 顶部集中定义。标"**实测**"的必须按实车量，标"**按线改**"的必须和接线一致。

| 参数 | 当前值 | 说明 |
| --- | --- | --- |
| `kWheelRadius` | 0.076 m | **实测**。4 寸全向轮（直径 152 mm）即此值 |
| `kHalfLength` | 0.190 m | **实测**。底盘中心到前/后轮轴线距离 |
| `kHalfWidth` | 0.190 m | **实测**。底盘中心到左/右轮轴线距离；正方形底盘与上者相同 |
| `kIdRf/Lf/Lr/Rr` | 1 / 2 / 3 / 4 | **按线改**。ID 顺序沿用 `omni/readme.md` 约定：右前=1、左前=2、左后=3、右后=4（绕底盘逆时针一圈）。必须与 C620 拨码一致，且四台同属 1~4 |
| `kReverseRf/Lf/Lr/Rr` | 全 `false` | 单个轮子转向反了就置 `true`，**不要改 omni 公式符号**。注意 `Omni` 构造参数顺序是 `(lf, lr, rf, rr)` |
| `kDt` | 1e-3 s | 必须与 `osDelay(1)` 一致，改循环周期要连它一起改 |
| `kMaxSpeed` | 1.5 m/s | 首次上电建议先降到 0.3~0.5 |
| `kMaxOmega` | 2.0 rad/s | 最大自转角速度 |
| `kStickDeadzone` | 0.05 | 摇杆死区，防中位抖动导致缓慢爬行 |
| `kKp / kKi / kKd` | 0.60 / 0.40 / 0 | 由第 5 节仿真确定，非随手填 |
| `kMaxTorque` | 1.2 N·m（≈4 A） | **单轮力矩上限，也就是实际"油门"**；提速先加这一项 |
| `kMaxIout` | 0.60 N·m | 积分限幅，至少要能兜住静摩擦 |
| `kIntegralPause` | 0.6 N·m | 积分分离阈值，约等于 2 rad/s 的误差 |
| `kMaxTotalTorque` | 3.6 N·m | 四轮力矩绝对值之和的兜底上限 ≈ 12 A ≈ 290 W @24 V |

## 6. 上电调试顺序

> 顺序不能跳，尤其是第 2 步之前一定保持**底盘悬空**。

1. 底盘垫起悬空；把 `kMaxSpeed` 降到 0.3、`kMaxTorque` 降到 0.5；
2. 只推**左摇杆左右**（wz）：四轮应同时朝同一方向滚动，与 `sp_middleware/tools/omni/readme.md`
   的 `reverse_xx` 标定表一致；某个轮子相反就把对应的 `kReverseXx` 置 `true`；
3. 只推**右摇杆上下**（vx）：左右两侧轮子**反号**——这是全向轮的正确定性（`LF=LR=-v/(r√2)`、
   `RF=RR=+v/(r√2)`），和麦克纳姆轮不同，不要误判成接反；
4. 落地慢速试 vx / vy / wz，确认车真的朝对应方向走。**走偏**优先怀疑 `kWheelRadius` /
   `kHalfLength` / `kHalfWidth` 量错；
5. 用调试器观察 `motor_lf.speed`、`pid_lf.out`、`g_chassis_power_w`；
6. 手感确认无误后，再逐步放开 `kMaxSpeed` 与 `kMaxTorque`。

## 7. 预留接口：超级电容 / 功率控制

硬件未就绪，当前只在软件侧兜底，接口位置：

| 接口 | 位置 | 现状 | 接入后要做什么 |
| --- | --- | --- | --- |
| `chassis_power_update(power_w)` | `chassis_task.cpp` | 每周期记录机械功率 `Σ\|实测转速 × 力矩\|` | ① 用裁判系统 0x0202 的缓冲能量算功率上限；② 把上限写进超电 |
| `chassis_apply_power_limit(torque[4])` | `chassis_task.cpp` | 固定 `kMaxTotalTorque` 等比缩放 | 换成由功率环算出的上限 |
| CAN 接收回调 | `HAL_CAN_RxFifo0MsgPendingCallback` | 只认 0x201~0x204 | 补 0x301/0x302（超电）等 ID 的分发 |

接入步骤（文件末尾也有同样注释）：

1. **超级电容**：`CMakeLists.txt` 加入 `sp_middleware/motor/super_cap/super_cap.cpp` → 建
   `sp::SuperCap super_cap;` → 在 CAN 回调里补 `super_cap.read(...)` → 在
   `chassis_power_update()` 里 `super_cap.write(...)` + `can1.send(super_cap.tx_id)`。
   注意**超电反馈是小端，与电机的帧格式相反**。
2. **功率上限（裁判系统）**：`CMakeLists.txt` 加入 `sp_middleware/referee/vt03/vt03.cpp`（或 `pm02`），
   从 0x0202 取功率上限与缓冲能量，替换 `kMaxTotalTorque`。
3. **若功率环带宽要求高于 1 kHz**：不要在 `chassis_step()` 里加循环，另开独立任务与独立 CAN 帧。

## 8. 已知遗留

1. **`dt` 与真实周期不完全相等**：`osDelay(1)` 的实际周期是"1 tick + 循环体耗时"，
   而 PID 的 `dt` 写死 `1e-3f`（仿真用的是严格 1 ms）。要严格化需先在
   `FreeRTOSConfig.h` 打开 `INCLUDE_vTaskDelayUntil`（当前为 0，`osDelayUntil()` 会**静默失效**），
   或把 `tools/timer` 的 DWT 计时加进编译后实测真实周期。
2. **CAN 的 `AutoBusOff` 仍为 DISABLE**：总线抖动导致 Bus-Off 后不会自愈。
   接上电机后建议在 CubeMX 里把 `Auto Bus-Off` 打开（详见 `docs/` 上一轮的代码疑点清单第 6 条）。
3. **`chassis_task.cpp` 依赖 `uart_task.cpp` 里的 `remote` 对象**（`extern sp::DBus remote`）。
   **不要**把 `uart_task.cpp` 从 `CMakeLists.txt` 移除，否则直接链接失败。
4. 云台（GM6020）控制尚未恢复：原 `can_task.cpp` 只做 0 V 占位，本轮已删除；
   后续做云台时按同样方式新建任务，并在 CAN 回调里补 0x205 的分发。
