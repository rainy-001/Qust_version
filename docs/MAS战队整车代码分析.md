## 1. 整车架构

**两块 STM32F407 C 板、裸机（无 RTOS）、各自一条控制热回路，靠 CAN2 对接。**

```text
                    ┌───────────── 云台板 (Master) ─────────────┐
  遥控器(DBUS) ─USART3─►│ Remote.c         摇杆 / 拨码 / 开关        │
  图传/VT03    ─USART6─►│ RefereeSystem.c  0x0304 键鼠 → Keyboard   │
  视觉(上位机)  ─USART1─►│ Visual.c         偏航/俯仰补偿（空架子）   │
  IMU(BMI088+IST8310)  │ AttitudeAlgorithms  TIM11 1kHz 官方 AHRS  │
                     │                                          │
                     │  TIM6 2ms：Pitch/Yaw 串级 PID + 摩擦轮 + 拨弹盘 │
                     └───────┬──────────────────────┬───────────┘
                      CAN1   │                      │  CAN2
               ┌─────────────┴────────┐              │
         Pitch 6020 (0x206)          │   Yaw 6020 (0x205)  ← 两块板都读
         拨弹盘 M2006 (0x207)        │   CToC 0x149 / 0x189 / 0x019
         摩擦轮 M3508 (0x201/0x202)  │              │
                                     │              │
                     ┌───────────── 底盘板 (Slave) ──────────────┐
                     │  摇杆/开关状态来自 CAN2 0x149 / 0x189       │
                     │  TIM6 2ms：PVI 功率模型 → 麦轮逆解 → 4×转速环 │
                     │  裁判系统 ─USART6─ 0x0201 / 0x0202         │
                     │  超电 ─CAN1 0x601 / 0x602 / 0x603（只发）    │
                     └────── CAN1：麦轮 M3508 ×4 (0x201~0x204) ─────┘
```

### 1.1 总线与串口分配

| 资源 | 云台板 | 底盘板 |
| --- | --- | --- |
| CAN1 | 发射/俯仰总线：Pitch 6020 + 拨弹 M2006 + 摩擦 M3508 ×2 | 麦轮 M3508 ×4 + 超电（只发） |
| CAN2 | **云台↔底盘互联总线**：Yaw 6020 反馈 + 三帧 CToC | Yaw 6020 反馈（只读）+ CToC |
| USART3 | DBUS 遥控器 100 kbps 8E1 + DMA 双缓冲 | 未启用（`Remote_Init()` 从未调用） |
| USART6 | 图传链路 115200 8N1（0x0304 键鼠） | 裁判系统 115200 8N1（0x0201/0x0202） |
| USART1 | 视觉通信 115200 8N1（PA9/PB7） | — |
| CAN 位时序 | 1 Mbps，PSC=3 / BS1=10tq / BS2=3tq（采样点 78.6%） | 同左 |

### 1.2 供电域【推断，依据掉电隔离逻辑反推】

- **云台供电**：Yaw 6020 + Pitch 6020 + 云台板
- **发射供电**：摩擦轮 M3508 ×2 + 拨弹盘 M2006
- 依据：发射机构掉电时保留 `0x206`（Pitch）、砍掉 `0x207`/`0x201`/`0x202`（见 §6.1）

### 1.3 一个很聪明的设计

Yaw 电机的反馈帧 `0x205` 挂在 CAN2 上，**两块板都把它放进自己的轮询列表**——
底盘因此不需要云台"转发"偏航角，直接读同一帧。省掉一层通信，也避免了转发延迟。
这是"总线即共享内存"的典型用法。

| --- | --- | --- | --- |
| TIM6_DAC | **2 ms**，PID 闭环 | **2 ms**，PID 闭环 | 全车唯一控制节拍 |
| TIM11 | **1 ms**，AHRS 姿态 | — | 云台独有 |
| TIM13 | 2.5 ms，CAN 链路看门狗 | 2.5 ms，同 | 收帧即复位（`LinkCheck_ON/OFF`） |

## 3. 云台控制链：IMU 全闭环的串级 PID

`Gimbal_MoveControl()` 每 2 ms 顺序执行四步：`PitchControl → YawControl → FiringMechanismControl → Rammer`。

### 3.1 串级结构与参数

| 轴 | 角度环反馈 | 速度环反馈 | 输出 | 参数（角度环 / 速度环） |
| --- | --- | --- | --- | --- |
| Yaw | `AttitudeAlgorithms_DegYaw`（带圈数展开） | `GM6020_MotorStatus[0].Speed` | CAN2 `0x1FF` 电压 | Kp=10, **Kd=20** / Kp=200, Kd=10 |
| Pitch | **`AttitudeAlgorithms_DegRoll`** ⚠️ | `GM6020_MotorStatus[1].Speed` | CAN1 `0x1FF` 槽2 电压 | Kp=6 / Kp=200 |

两环都是 `Ki = 0`，输出限幅：角度环 ±200 / ±150，速度环 ±30000（GM6020 电压满量程）。

### 3.2 最反直觉的一处：Pitch 用 Roll 角

Pitch 环的反馈用的是欧拉角的 **Roll** 分量，不是 `DegPitch`。
`Hardware/BMI088.c` 里**没有任何轴交换**（原始加速度/角速度直接除以标度因数后喂给 AHRS 库），
说明 IMU 是**侧装/旋转 90°** 安装的，云台俯仰在欧拉角里体现为 roll。
限位宏 `Pitch_GM6020AngleUpperLinit = -40°` / `LowerLinit = +10°` 也印证"抬头 = Roll 变负"。

> **维护陷阱**：后来的人如果盯着 `DegPitch` 调 Pitch 参数，会发现怎么调都没反应。

### 3.3 绝对姿态闭环的取舍

云台始终以 IMU 角度为目标，因此**小陀螺时枪口自然稳定**（作者在 README 里说"没必要考虑
小陀螺特殊处理"，这个判断是对的）。代价是：

- IMU 漂移 = 云台漂移。这直接对应作者的遗留问题 8「Pitch/Yaw 低频抖动」。
- `Kd = 20 / 10` 作用在**带噪声的 IMU 角速度**和**整数 rpm** 的编码器反馈上，会把量化噪声放大成输出抖动。
- 目标值是"增量累加"式的：`Need_Value -= Gimbal_LeverSpeedMapRate/8192*360`，摇杆被当作速度输入积分成角度。
  累加本身没有总限幅，靠 `DegRoll` 的上下限条件阻止继续累积。

### 3.4 视觉补偿（未联调）

`Visual.c` 用 `0x09 0x14 + Yaw×100 + Pitch×100 + 0x18` 的无校验简单帧，
收到后直接改写 `Gimbal_YawAnglePositionPID.Need_Value`。作者自述视觉组未出成果，这段从未联调。
`Visual_Pitch/Yaw` 没有范围检查，丢一帧就会插进一个错误角度。

## 4. 发射机构链：一帧里混装两种电机

### 4.1 `0x1FF` 的双重身份

**M2006 的高位 ID 帧 `0x1FF` 与 GM6020 的低位 ID 帧 `0x1FF` 是同一个标识符。**
于是 `Gimbal_Rammer()` 的最后一行同时干了两件事：

```c
M2006_CANSetHIDCurrent(0, Gimbal_PitchAngleSpeedPID.OUT, Gimbal_RammerSpinSpeedPID.OUT, 0);
//                      ↑槽5        ↑槽6 = Pitch 6020 的电压         ↑槽7 = 拨弹盘 M2006 的电流
```

- `data[2..3]` 既是"ID6 电机电流"也是"GM6020 ID2 电压" → 装 Pitch 电压
- `data[4..5]` 装拨弹盘电流

**后果：Pitch 的控制帧由拨弹盘函数代发。** `Gimbal_Rammer()` 一旦被跳过，
Pitch 轴立刻失去指令；而函数名 `M2006_CANSetHIDCurrent` 完全掩盖了第二个参数是电压这件事。
这是整套代码里**最容易被后续维护者改坏的地方**。

### 4.2 摩擦轮 / 拨弹盘 / 激光

| 项目 | 电机 | 目标 | PID | 备注 |
| --- | --- | --- | --- | --- |
| 摩擦轮 ×2 | M3508 (0x201/0x202) | ∓7500 rpm（弹速限 30 m/s） | Kp=16, **Kd=30**, 输出 ±15000 | 左负右正（镜像装配）；开摩擦轮同时开激光 |
| 拨弹盘 | M2006 (0x207) | ±5400 rpm | Kp=16, 死区 ±20, 输出 ±30000 | "射频 20 的最低下限"；**无堵转保护** |
| 激光 | PC8 推挽 | 高电平点亮 | — | 与摩擦轮联动 |

使能条件：`(Remote_LS==1 || PC_FrictionWheel==1) && RefereeSystem_ShooterStatus==1`
——发射机构未上电时，摩擦轮和拨弹盘都被禁止（符合赛规）。

**堵转问题**：拨弹盘卡弹时 PID 会把电流顶到 ±30000 满量程并一直保持，没有任何堵转检测。
这正是作者遗留问题 5「Pitch 轴 6020 容易卡弹丸导致堵转」同类问题（Pitch 被卡时同样无保护）。

## 5. 底盘控制链：自研 PVI 功率模型

详见 `docs/底盘控制链路实现说明.md`（针对 Qust 版的逐行拆解，公式同源），这里只做整车视角评价。

| 环 | 职责 | 实现 | 评价 |
| --- | --- | --- | --- |
| 功率环 | 定功率上限 | `Buffer/30 × Ref`，×摇杆幅度，硬限 150 W，超电 +100 W | "用缓冲能量当积分器"思路正确（飞坡 250 J 能吃满），但 30 J 基准与 4× 上限纯经验 |
| 速度环 | 用**增益系数**缩放速度指令逼近功率上限 | `GainCoefficient` 0.5→2.0，10 ms 周期，步长 0.02/0.05 | 停车立刻归 0.5 → 起步功率突增，是架构固有抖动 |
| 电流环 | 总电流软限幅 | `I = P×512/15`，1×~6× 插值，四路等比缩放 | 系数 `×5`、`B=20 J`、`±5 W` 死区均无标定依据 |

**功率估算的量纲是对的**：`Power = ShaftSpeed(rpm) × Current(A) × 0.3/9.55`，
其中 `0.3 N·m/A` 是大疆给出的**输出轴**转矩常数，与 `P = T·ω` 严格一致（已核算）。
问题在于：乘了个经验系数 `√3 ≈ 1.732` 补偿效率/铜损，且**全车没有电压采样**
（底盘板无 ADC 测电池电压），电池从 25.2 V 掉到 22 V 时功率估算会系统性偏小。

**四轮总电流被限到约 16384 counts（≈20 A 总、四轮平均 5 A）**，
这是作者遗留问题 2「底盘跟随速度很慢」的直接原因之一。

## 6. 板间通信

### 6.1 协议

云台（主）主循环 1.5 ms 发两帧，底盘（从）主循环 2 ms 回一帧：

| ID | 方向 | 内容 | 周期 |
| --- | --- | --- | --- |
| `0x149` | 云台→底盘 | 右摇杆 RL/UD、左摇杆 RL/UD（键鼠模式下被换算成等效摇杆值） | 1.5 ms |
| `0x189` | 云台→底盘 | 遥控连接状态、右拨码、Ctrl/Shift 开关态、启动标志、左拨码 | 1.5 ms |
| `0x019` | 底盘→云台 | **只有 1 字节有用**：发射机构是否上电 | 2 ms |

设计上把"摇杆量"和"开关/状态"拆成两帧；键鼠模式下云台把 WASD/鼠标换算成 0~2048 的
**等效摇杆值**再发，底盘侧完全不需要知道用的是遥控器还是键鼠——这一点做得很干净。

注意 ID 命名方向是反的：云台（主）发送时用的 `StdId` 是 `CToC_SlaveID1/2`，
即"这个帧装的是哪个从机需要的数据"，而不是发送方身份。

### 6.2 亮点：发射机构掉电的 CAN 自动隔离

发射机构未上电时 M2006/M3508 不响应，轮询链会一直卡在它们身上报错。
解法（云台 `LinkCheck.c` 超时中断）：

```c
if (RefereeSystem_ShooterStatus == 0) {          // 发射机构未上电
    CAN_CAN1DeviceNumber = 1;                    // 只保留 index0 = Pitch 0x206
    CAN_DeviceNumber     = 3;                    // Pitch + Yaw + CToC
    CAN_CANIDReset();
} else {
    CAN_CAN_GetRefereeSystemData();              // 只等 0x019，收到后从 0 重新开始
}
```

等 `ShooterStatus` 变 1 后（在 CAN 接收中断里）数 5000 帧再把设备加回来，
用来等 C620 电调启动。**这是全套代码里最"懂硬件"的一段。**

### 6.3 亮点：用 CToC 帧给轮询链重新对齐

任意设备掉线后把 `CAN_IDSelect` 直接跳到"只等 `0x019`"，收到后再从 0 重新开始。
用一个"慢但可靠"的帧当同步点，比猜"下一个该是谁"稳。

## 7. 缺陷清单

### A 级：会直接导致比赛失利

**7.1 图传/遥控器双链路的仲裁是坏的（最严重）**

`Remote.c` 的 `USART3_IRQHandler`（遥控器）和 `RefereeSystem.c` 的 `USART6_IRQHandler`（图传）
**复位同一个 TIM7 看门狗**，而 `RefereeSystem_Status` 只有在 TIM7 超时时才清零：

```c
// Remote.c: TIM7 超时才清两个标志
void TIM7_IRQHandler(void) {
    RefereeSystem_Status = 0;   Remote_Status = 0;   Remote_StartFlag = 1;
}
```

→ **只要遥控器在线，图传断开后 `RefereeSystem_Status` 永远是 1**，
于是所有 `... && RefereeSystem_Status == 0` 的遥控器分支永久失效，**遥控器再也控不了车**。
这就是 README 那句"上电后注意不要更改控制方式"的真实根因。

此外 `Remote_RxData` 的鼠标/键盘字段被两个解析器（`Remote_DataProcess` 与 `Keyboard_DataProcess`）
同时写，谁后到谁赢；两者按键位序恰好兼容，但语义来源不一致。

**7.2 恒温控制是死代码**

`IMUTemperatureControl_Init()`（TIM10 / PF6 加热 PWM）**全工程零调用**，
`IMUTemperatureControl_OpenFlag` 恒为 0 → TIM6 里的恒温闭环 `if (...OpenFlag == 1)` 永不执行。
加热电路做了但没启用——**这正好对应遗留问题 9「IST8310 初始化有时过不去」**（低温下 IMU 起不来）。

更麻烦：一旦启用，`BMI088_Temperature > 50` 分支是 `while(1){报警; PWM=0}` **且不喂狗**
→ IWDG 1.02 s 复位 → 温度仍高 → **无限重启**。

**7.3 单板失效即整车瘫痪，无降级**

- 云台板死 → 底盘收不到摇杆 → `Remote_Status=0` → 四轮 0 电流
- 底盘板死 → 云台收不到 `0x019` → 2.5 ms 超时 → `LinkCheck_Error=1` → 云台全体 0 电流
  + 发射机构状态永远未知（摩擦轮/拨弹盘永久禁用）

两板之间没有任何心跳冗余或降级策略。

**7.4 2.5 ms 链路检测 vs 2 ms 的 `0x019` 周期，余量只有 0.5 ms**

底盘主循环的 `CToC_SlaveSendRefereeSystemData()` 带忙等（最多 0xFFF 次），
一旦 CAN2 邮箱拥堵或主循环被 `Delay_us(2000)` 拉长就会踩线 → 云台误判断线 → 全车停产。
这是"偶发整车停摆"的典型来源。

### B 级：隐患

| # | 问题 | 位置 |
| --- | --- | --- |
| 7.5 | `CAN_CAN1DeviceNumber` / `CAN_IDSelect` 在中断里被改又被读，状态机是隐式的，改一行就可能死循环 | 云台 `CAN.c` / `LinkCheck.c` |
| 7.6 | 摩擦轮/拨弹盘无堵转保护，卡弹时 2 ms 周期持续给满量程电流 | 云台 `Gimbal.c` |
| 7.7 | `Gimbal_YawAngleSpeedPID` 硬编码 `GM6020_MotorStatus[0]`，与同函数里的 `[Gimbal_PitchMotor-0x205]` 风格不一致，换电机 ID 会漏改 | 云台 `Gimbal.c:140` |
| 7.8 | Pitch 限位用两套坐标：累加判断用 `DegRoll`（角度），视觉补偿判断用 `GM6020.Position`（编码器计数），两者靠魔数 `3245` 换算，无法互相校验 | 云台 `Gimbal.c:98-105` |
| 7.9 | **鼠标位移增量被当成"速率"重复消费**：`Remote_Mouse_RL` 是"每帧位移"，每个 2 ms 周期都累加一次，直到下一帧到达。实际转角 ∝ 控制频率/图传帧率，图传帧率一抖就被感知为"延迟/不跟手" | 云台 `Gimbal.c:126-135` |
| 7.10 | 视觉帧无校验、无范围限制 | 云台 `Visual.c` |

> 7.9 的量化：`Δangle = 0.0439453125 × 7 × 1.5² × (Mouse×3/660×2) ≈ 0.00629 × Mouse` 度/2 ms 周期。
> 500 Hz 下等价 `3.15 × Mouse` °/s。Mouse 是"每帧位移"，若图传 50 Hz，则每帧转角
> = 0.00629×Mouse×10 周期 —— **转角取决于帧率之比**，这是设计缺陷而非参数问题。

## 8. 作者自述 9 条问题 → 代码根因对照

| # | 作者自述 | 代码中的根因 |
| --- | --- | --- |
| 1 | 定时器和中断优先级尽量不要改，裸机开发改不好容易疯车 | 全车逻辑挤在 2 ms 中断里，控制/通信/报警无优先级隔离 |
| 2 | 底盘跟随速度很慢，转弯有扭动 | `Mecanum_TrackPID` Kp=0.004 + 输出限幅 ±5；且四轮总电流被限到 ≈20 A |
| 3 | 鼠标控制延迟比较大 | §7.9 位移增量被当速率重复消费，转角取决于图传帧率 |
| 4 | 飞坡后 250 J 缓冲能量还能更好利用 | `PowerRef` 上限 4× → 功率上限最多 150 W，未针对 250 J 做专门策略 |
| 5 | Pitch 轴 6020 容易卡弹丸导致堵转 | §7.6，无堵转检测/保护 |
| 6 | 反向小陀螺还可以改，加过渡过程 | 反向小陀螺（`RS==1`）直接给常值 ±5 rad/s，没有像正向那样的"待关闭"过渡态 |
| 7 | 遥控器和图传链路兼容有问题，图传检测时间没精调 | §7.1 共享看门狗 + 共享结构体，无显式模式状态机 |
| 8 | Pitch/Yaw 6020 还有一些小幅低频抖动 | §3.3，IMU 绝对闭环 + 大 Kd + 整数 rpm 反馈 |
| 9 | IST8310 初始化有时过不去会报警 | §7.2，恒温控制从未启用，低温下 IMU 起不来 |

**9 条里有 8 条能在代码里定位到具体根因**，其中 7.1 / 7.2 / 7.9 是"实现缺陷"而非"参数没调好"。

## 9. 总体评价

### 做得好的

1. **架构切分清晰**：云台/发射一块、底盘一块，谁碰电机谁就拿那条总线；
   CAN2 既做互联又承载共用的偏航反馈，省掉一层转发。
2. **输入抽象干净**：键鼠/遥控器在云台侧统一换算成摇杆等效值，底盘对此无感。
3. **有硬件级思考**：发射机构掉电的 CAN 隔离、用 CToC 帧给轮询链重新对齐。
4. **文档与注释到位**：24 KB README 带公式、推导、图像和局限性自述；每个 .c 文件头有完整注释块。
5. **CAN 位时序规范**：1 Mbps / 采样点 78.6%，比同期的很多开源工程更合理。

### 短板集中在"状态机"

缺陷几乎都不是算法问题，而是**缺少显式的运行模式状态机**：

- 双链路仲裁靠共享一个看门狗变量 → §7.1
- 掉线隔离靠改全局计数 → §7.5
- 恒温靠一个从未置位的 flag → §7.2
- 鼠标输入靠"最后一个增量持续生效" → §7.9

如果当初有一个 `enum { RC, VT03, RC_LOST, VT03_LOST }` + 各自时间戳，作者自述的问题 1、7、9 都不会存在。

### 对本队（Qust 版）可借鉴的三点

1. **CAN 掉线要做"设备级隔离 + 自动恢复"**，而不是一票否决全部电机
   （MAS 的做法虽是全局停机，但至少区分了"发射机构未上电"这种正常态）。
2. **功率控制优先做"速度环输出端的功率反馈"**，不要复刻 MAS 这套
   "三段查表 + 经验系数"的插值；MAS 的 `×5` / `B=20 J` / `±5 W` 全部无标定依据。
3. **输入源只允许一个"说话的人"**：遥控器、图传、视觉必须走一个带时间戳的仲裁层，
   绝不能让多个 ISR 往同一个 `Remote_RxData` 里写。
