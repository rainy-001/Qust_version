# 代码注释说明（`// [解析]` 标记）

本文说明本次新增注释的**标记约定**、**覆盖范围**、**如何只看自己的代码**、
**如何一键删除**，以及**验证方式**与**过程中发现的代码疑点**。

---

## 1. 为什么要有这个约定

本项目的 `sp_middleware/` 来自**同济 SP 战队开源的 RoboMaster 电控中间件**，
`Core/` 大部分是 **STM32CubeMX 自动生成**的 HAL 代码。

这两部分都**自带大量原注释**（doxygen 块、CubeMX 的 `/* USER CODE BEGIN */` 标记、
原作者的中文说明）。直接往里加注释会导致"分不清哪句是原作者写的、哪句是后来补的"，
改代码时既容易误删原注释，也容易破坏生成代码的保护标记。

所以约定：**所有后来新增的解释性注释，一律以 `// [解析] ` 开头。**
（半角方括号，方括号后跟一个空格）

---

## 2. 标记长什么样

**整行注释**：

```cpp
// [解析] 这一帧最多带 8 字节数据，所以数组长度是 8。
uint8_t tx_data[CAN_DATA_LEN];
```

**行尾追加注释**：

```cpp
  tx_header.RTR = CAN_RTR_DATA;  // [解析] 表示这是"数据帧"，不是远程请求帧
```

**文件开头的说明块**（每个文件都有）：

```cpp
// [解析] ==========================================================================
// [解析] 【文件】sp_middleware/io/can/can.hpp
// [解析] 【作用】把 STM32 HAL 库那套繁琐的 CAN 操作，封装成一个好用的 CAN 类。
// [解析] 【被谁用】applications/can_task.cpp：sp::CAN can1(&hcan1); 创建对象。
// [解析] 【关键点】过滤器全通配；标准帧/扩展帧靠 IDE 位区分；tx_data 是共享缓冲区。
// [解析] ==========================================================================
```

**连续多行时每一行都要重复 `// [解析] ` 前缀**，这样整段折叠/删除时不会漏。
发现可疑代码时用 `// [解析] 注意：...` 标出。

## 4. 怎么只看"自己的代码"

`[解析]` 这个标记在全项目里是唯一的，所以过滤很干净。

**隐藏全部新增注释，只看原有逻辑**：

```bash
grep -v '\[解析\]' applications/can_task.cpp                   # Git Bash / Linux / macOS

Select-String -NotMatch '\[解析\]' applications\can_task.cpp    # PowerShell
```

**只显示新增注释（当学习笔记读）**：

```bash
grep -n '\[解析\]' sp_middleware/io/can/can.cpp

Select-String '\[解析\]' sp_middleware\io\can\can.cpp
```

**VS Code**：直接全局搜索 `[解析]`，即可列出所有新增注释的位置。

**看每个文件加了多少行**：

```bash
git diff --numstat        # 第一列=新增行数，第二列=删除行数
```

## 5. 怎么撤销 / 删除这些注释

**最安全、最推荐的做法**——直接丢弃这次改动，回到加注释之前：

```bash
git checkout -- applications Core sp_middleware
```

**只想删掉新增注释行、保留其他改动**（先预览再执行）：

```bash
# 预览
grep -rn '\[解析\]' applications Core sp_middleware | wc -l

# 就地删除（建议先 git commit 或备份）
grep -rl '\[解析\]' applications Core sp_middleware | xargs sed -i '/\[解析\]/d'
```

> ⚠️ `sed -i '/\[解析\]/d'` 删除的是**整行**。
> 对"行尾追加注释"的行（`代码;  // [解析] ...`），整行会被一起删掉，**代码就丢了**。
> 本项目绝大多数是整行注释，但仍有约 40 处行尾注释，
> 所以**批量删除后务必 `git diff` 检查一遍**，或直接用上面的 `git checkout --`。

## 7. 验证方式（怎么确认"逻辑零改动"）

本次改动通过了**四层独立验证**：

| # | 验证 | 方法 | 结果 |
|---|---|---|---|
| 1 | 宽松源码比对 | 剥离所有注释与空白后比较代码字符流（字符串字面量内容也参与比较，`build/verify_comments.py`） | 125/126 文件**逐字符一致**；唯一差异是刻意修复的 `vision_task.cpp` |
| 2 | 严格源码比对 | 保留缩进、逐行比对代码行（`build/verify_strict.py`） | 同上 |
| 3 | **二进制比对** | 重新编译后对比 `.text` / `.rodata` / 去调试 ELF / 完整 bin 的 SHA256 | 四项**全部逐字节相同**；FLASH 占用 52388 B 与改动前一致 |
| 4 | 逐文件编译回归 | 对 50 个 `.c/.cpp` 分别编译 HEAD 版本与当前版本，比较错误信息集合（`build/verify_compile.py`） | **0 个新错误**；47 个零错误零警告；2 个是同一个既有错误；1 个改善 |

`.text` 段哈希（改动前后一致）：
`5093596EC9752FB4E70CE0C595EF99A3F873ADF6D015C5410F77396B15C98032`

复现验证（脚本位于 `build/`，该目录已在 `.gitignore` 中）：

```bash
python build/verify_comments.py     # 宽松：剥离注释后代码一致性
python build/verify_strict.py       # 严格：保留缩进的逐行比对
python build/verify_compile.py      # 编译回归对比
cmake --build build/Debug           # 全量重编译
```

> 说明：验证 3（二进制）只覆盖真正参与链接的文件；未加入 `CMakeLists.txt` 的模块

## 8. 过程中发现的代码疑点（**均只标注、未修改代码**）

以下按"值得优先确认"排序，详细说明都写在对应源码的 `// [解析] 注意：` 处。

### 会影响正确性的

1. **`rm_motor.cpp` 减速比被算了两遍、相互抵消**：`get_raw_to_torque()` 里已除过 `ratio_`，
   `read()` 里又乘了一次，于是 M2006/M3508 读回的 `torque` 与手册 N·m **对不上**。
   `cmd()` 方向自洽，所以闭环能用，只是绝对值不可对账。
   另外 `*10` / `*20` / `*3` 三个系数的来历在官方手册里找不到依据。
2. **`bmi088.cpp` 陀螺仪标度因数公式疑似笔误**：
   `2000.0f / (BMI088_GYRO_RANGE_SET + 1) / 32767` 应为
   `2000.0f / (1 << BMI088_GYRO_RANGE_SET) / 32767`（满量程是 `2000/2^n`）。
   本项目固定用 2000dps（n=0），所以**当前结果正确**，但改小量程后角速度会整体偏大。
3. **`fuzzy_pid.cpp` 的 D 项少了 `/ dt_`**：`pid.cpp` 里是 `kd_ * dbuf[0] / dt_`，
   模糊版是 `fuzzy_kd * dbuf[0]`。两者 `kd` 量纲差一个 `dt_`（1kHz 下 1000 倍），
   **参数不能互相照抄**。
4. **`ddt_motor.cpp` 角度除数是 32767 而非 65535**：`angle_int` 是 uint16，
   除以半量程后角度会一路涨到约 4π 再被折回，很可能应为 65535。
5. **`diff_drive.cpp` 的 `update()` 旋转速度符号疑似写反**：
   `(sign_l_*speed_r - sign_r_*speed_l)` 应为 `(sign_l_*speed_l - sign_r_*speed_r)`；
   原地自转时算出的 `w` 符号与物理相反（前进速度 `v` 不受影响）。
   该模块目前**全工程无人调用**，所以一直没暴露。
6. **`joint_controller.cpp` 的 `init_angle_` 未乘 `sign_`**：
   `pos = sign_ * motor_.angle - mid_ - init_angle_`，当 `reverse = true` 时
   零点位置与直连情况不对称，疑似笔误。
7. **`vision.cpp` 溢出处理不完整**：`update()` 只把 `rx_len_` 清零；
   若单次 `len` 本身大于 `rx_buffer_` 的 512 字节，紧接着的 `std::copy` 仍会越界写内存。
8. **`led.cpp` 亮度顶到 1.0 会溢出**：算的是 `(ARR+1) * 亮度`，ARR 固定 65535，
   填 1.0 得 65536，超过 16 位 CCR 上限被截断（可能表现为灯灭而非最亮）。
   另外通道与颜色对应是 **CH1=蓝、CH2=绿、CH3=红**，与 `set(r,g,b)` 顺序不一致。

### 编译 / 构建层面的

9. **`printf` 目前是"没接上"的状态**：`syscalls.c` 里 `__io_putchar` / `__io_getchar`
   只有 `weak` 声明、全工程**没有任何定义**。一旦有代码真的调用 `printf`，
   会跳到 0 地址触发 **HardFault**。想用串口打印必须自己实现 `__io_putchar`。
10. **`syscalls.c` / `sysmem.c` 没有任何 `USER CODE` 保护区**，
    重新用 CubeMX 生成代码会被**整份覆盖**，手写代码不能放在这两个文件里。
11. **引脚信息有两处来源**：`applications/imu_task.cpp` 里硬编码了
    `GPIOA, GPIO_PIN_4` / `GPIOB, GPIO_PIN_0`，没有用 `main.h` 的宏。
    改引脚必须同时改两处，只改 `main.h` 不生效。
12. **`system_stm32f4xx.c` 里 `HSE_VALUE` 的兜底值仍是 25 MHz**（本工程是 12 MHz）。
    因为 `stm32f4xx_hal_conf.h` 已定义 `HSE_VALUE`，所以现在不生效、编译器也不报警；
    一旦该定义或 `USE_HAL_DRIVER` 变动，波特率与 CAN 位时序会整体偏 25/12 倍。
13. **`INCLUDE_vTaskDelayUntil = 0`**：调用 CMSIS 的 `osDelayUntil()` 不会报编译错误，
    但运行时会直接返回错误码（**静默失效**）。需要严格周期任务时要改成 1。

### 硬件配置 / 文档不一致

14. **SPI1 的 MISO 引脚，文档与代码矛盾**：`docs/C板引脚配置说明.md` 写 `PB3/PA6/PA7`，
    而 `spi.c` 与 `.ioc` 实际是 **PB4**。按文档接线会读不到 IMU。
15. **PB3 / PB4 复位后默认是 JTAG 引脚**（PB3=JTDO、PB4=NJTRST），
    全工程未见 `__HAL_AFIO_REMAP_SWJ_NOJTAG()` 调用。若 IMU 读不到数据，优先怀疑此处。
16. **ADC3 采样时间与文档不符**：文档写 56 cycles，`adc.c` 实际是
    `ADC_SAMPLETIME_3CYCLES`。电池分压网络阻抗较高，3 个周期可能充不满采样电容，
    导致电压读数偏低/跳动。
17. **SPI1 波特率 10.5 Mbit/s 略超 BMI088 的 10 MHz 上限**（APB2 84MHz / 8）；
    改 `SPI_BAUDRATEPRESCALER_16` 得 5.25 Mbit/s 更稳妥。
18. **`can.cpp` 打开了 RX_FIFO1 的中断通知，但 `can.c` 只使能了 `CAN1_RX0_IRQn`**，
    工程里也没有 FIFO1 的回调函数——这段配置实际是空的（"死配置"）。
19. **TIM1 被 HAL 时基独占**：`PSC=167 / ARR=999` 已锁死，
    而文档第 7 节又把 `TIM1_CH1~CH4`（舵机 PWM，PE9/PE11/PE13/PE14）列为可扩展项。
    二者**不能并存**：启用 TIM1 PWM 时改 `ARR/PSC` 会把 1ms 时基弄不准。
20. **`can.c` 里 `AutoBusOff = DISABLE`、`AutoRetransmission = DISABLE`**：
    进入 Bus-Off 后不会自动恢复、出错帧直接丢弃。赛场掉帧可考虑打开。

### 健壮性 / 边界

21. **`super_cap` 的 `is_alive()` 缺少首帧保护**：构造函数未初始化 `last_read_ms_`，
    且不像 `RM_Motor` 那样先用 `is_open()` 短路，上电收到第一帧前调用会拿随机值做减法。
22. **`vt02` 只处理 `0x0302`**，`mouse` / `keys` 两个公开成员**永远是默认值**；
    且 `memcpy` 前未校验 `data_len`（对比 `vt03` 有 `if (data_len != sizeof(...)) break;`）。
23. **`vt03::update()` 在 CRC 校验之前就置 `has_read_/last_read_ms_`**，
    于是收到任意一个字节（哪怕 CRC 全错）`is_alive()` 就为真。
24. **`referee/ui` 的 `Element` / `UI_Manager` 构造时不清零内部结构体**，
    必须定义成全局/静态对象（静态存储期会先零初始化）；定义在栈上会发出脏数据。
25. **`crc.cpp` 的 `check_crc8/check_crc16` 缺长度下限保护**：
    传 `len=0` 时 `len-1` 会提升为 -1 再转成 65535，导致巨量越界读。
26. **`math_tools.cpp` 的 `float_to_uint` 不限幅**，超量程会算出超出 `2^bits-1` 的值；
    `dm_motor.cpp` 的 `data[6] = torque_uint >> 8` 依赖"12 位结果右移 8 位必 ≤ 0xF"，
    一旦超量程该前提即被破坏。
27. **`cybergear_motor`：`CYBERGEAR_MAX_SPEED = 30.0f` 而其行尾原注释写 300rpm（=31.42 rad/s）**，
    相差约 4.5%；且这些量程宏在类里**其实没被使用**（真正生效的是构造参数），
    属于"看着能配、其实配不动"。
28. **`lk_motor.cpp` 的 `get_ecd_range()` 两个 switch 分支返回值完全相同**，
    整个函数等于没有分支；`LK_ECD_RANGE_14BIT/15BIT` 定义了却从未使用。
29. **`mahony.hpp` 的 `dq[4]`、`acc_euler[3]` 全工程搜索不到赋值处**，
    头文件却写成"只读输出"，实际读到的是未初始化内存。
30. **各驱动普遍忽略 HAL 返回值**（SPI/串口收发、GPIO 写），
    SPI 出错时表现为"读到上次的旧数据"而不是报错，现场排查困难。
